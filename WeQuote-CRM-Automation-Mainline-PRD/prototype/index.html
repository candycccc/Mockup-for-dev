      WeQuote CRM — Leads & Deals · Requirements

      v1.0 draftCandy · Product/UX4 Jul 2026 Audience: Engineering (Robert's team)

      Consolidates PRD v0.9 + all agreed amendments. Everything marked demo is clickable in this prototype — start at Leads.

      1 Positioning2 Data model3 Automation 4 UI5 Permissions6 Zoho7 Reporting 8 Acceptance9 Roadmap10 Open questions11 Out of scope

      1Positioning & problem

      The CRM is used by WeQuote's dealer users (AV integrators, e.g. LCR Integrated Systems) to manage their own end customers' leads and deals. It is not an internal WeQuote-staff tool. Per Lee Roche: CRM is a dedicated section, separate from Quote & Sales.

      Problem: WeQuote only tracks a sale once a Quote exists — no pre-quote prospects, and no object grouping option quotes of one opportunity. Result: pipeline value overstated (options double-count), win rate understated (each declined option counts as a loss), pre-quote opportunities live in email/memory.

      Goal: add Lead + Deal in front of the Quote → Project chain, with deal state derived from quote events, plus pipeline UI and reporting.

      Non-goals (Phase 1): custom objects, automation builder, email sync, standalone People object, weighted forecast, AI scoring/enrichment/summaries (Ask Ava / AI Overview in designs are Phase 2+ vision).

      2Data model

      2.1 Lead demo

      FieldNotes
      title"Lead Title" in the inbox. Derived from org/contact if not entered Q8
      contact_name / job_titlePrimary contact person (required) + role
      organisation_nameSeparate field from contact_name — never one free-text blob (§2.6)
      phone / emailAt least one required
      labelsCold / Warm / Hot (multi-select)
      interestsProduct categories: Television, CCTV, Lighting, Home Cinema, Networking… (org-extendable)
      site_addressPostcode search + manual; feeds Phase-3 map view
      sourceOrg-configurable enum. Seed: word of mouth, contractor, designer, website, social, referral, exhibition, phone-in, other
      owner / statusOwner defaults to creator. Status: open, converted, discarded (+ discard_reason)
      est_valuePrioritisation aid only; never in pipeline reports; carried to the deal on convert
      next_activityPhase 2 lead-level activities; until then show Created/Age
      • L1 — Lead creation creates the Customer. Same transaction, flagged prospect = true; default Customers list filters prospects out; flag clears on first deal/quote/project. demo
      • L2 — Duplicate check at lead creation. Fuzzy-match as you type; choosing a match attaches instead of creating a prospect.
      • L3 — Convert creates only the Deal (customer already linked); deal name = lead title, est value carried; lead becomes converted + read-only. demo
      • L4 — Discard needs a reason; discarded leads leave all lists/reports except a discard count.

      2.2 Deal

      One business opportunity for one customer; owns the pipeline stage; quotes attach to it. Fields: name, customer, owner, stage, estimated one-off + recurring values (P1 recurring = manual only; P2: suggested from history), value_locked, risk_notes, lost_reason, expected_close_date.

      Deal↔Quote: nullable deal_id + scope_group_id on Quote (quotes without deals unchanged). Deal↔Project: deal_projects join table — schema lands in Phase 1; richer UI Phase 4.

      2.3 Stages

      Org-configurable; seed: Enquiry → Site survey → Design/spec → Proposal sent → Negotiation + fixed Won/Lost. Every transition recorded in deal_stage_events (from P1) for future time-in-stage reporting.

      2.4 Scope groups demo

      Named buckets of quotes in a deal. Same group = mutually exclusive options → group value = ★ primary quote (default: latest sent; override logged). Different groups are additive. Q9 draft-only group value rule.

      2.5 Deal value

      • No quotes → manual estimates. Quotes exist → Σ primary values per group (deal_value_confirmed excludes likelihood=maybe).
      • Won → frozen at accepted amounts (change orders are project metrics, never sales). Lost → frozen for lost-value analysis.

      2.6 Customer: type + structured naming

      Customer gets explicit type: Organisation / Individual. Every entry point captures person and organisation as separate fields (lead form is the template). Duplicate check matches both. Legacy data untouched in P1 — cleanup via the Merge duplicates tool Phase 2.

      3Automation rules must-have

      Deal state derives from actions users already take while quoting — never manual board upkeep. Not shippable without all five. demo (convert → create quote → accept in the prototype)

      • A1 First sent quote → deal forward to "Proposal sent". Never auto-backwards.
      • A2 Quote accepted → group accepted, value frozen.
      • A3 Sibling Quotes → system status Rejected: excluded from signed totals, still retained in the Deal audit history, and can later be accepted to replace the current Winner.
      • A4 All groups resolved & ≥1 accepted → Won, value locked, skippable pre-filled Project prompt. All dropped → Lost (reason required).
      • A5 30 days no activity (org-configurable) → owner nudge via existing notifications; cards show days-since-activity, dimmed past threshold.
      Quote eventDeal effect
      In Progress / In Review / Passed ReviewNone (pre-send). Optional A0 [proposal]: first quote created → Design/spec
      Sent (first on deal)A1 → Proposal sent
      AcceptedA2 group accepted + A3 sibling Quotes rejected
      CompleteNone — fulfilment status; deal was Won at acceptance
      CancelledOut of group value. Cancelled ★primary → fall back to latest Sent in group (logged). Whole group cancelled → prompt owner to mark dropped, never automatic
      RejectedSystem-set on sibling Quotes via A3; accepting another Quote changes the Winner
